# Design and acceptance boundaries

Documents are user-supplied UTF-8 `.txt` and `.md` files. Each collection uses a single embedding model and vector dimension. Character windows with overlap retain original text, document identity, version and ordinal. Source IDs identify a specific chunk version; replacement and deletion invalidate stale source URLs.

The SQLite database holds original documents, chunks and embedding vectors. Retrieval scans only the selected collection, calculates exact cosine similarity, and uses stable tie breaking. This is a persistent vector database with linear search, intended for small local FAQ corpora rather than millions of chunks. A configurable top-k supplies sources to the generator. Similarity does not establish whether a question is answerable.

Ollama provides local embeddings and JSON generation. Defaults are `nomic-embed-text` and `qwen2.5:3b`; explicit generation-model overrides remain supported. The application rejects remote endpoints, redirects, invalid vectors, malformed generation and citations outside the retrieved set. Imported document text is untrusted evidence, never a trusted instruction.

Answers are extractive: a real model selects supporting quotes, and the application returns the selected source wording rather than a generated paraphrase. The model workflow separates planning, evidence selection and review:

1. Plan atomic requests from the original question without document context. The prompt asks to copy single questions unchanged and split only explicit compound clauses, preserving qualifiers. The application assigns fixed outer request IDs, bounds the plan to 16 requests, and rejects duplicate or malformed requests.
2. Select evidence separately for each planned request. Each call sees only that request under a local `P1` ID and the retrieved passages under request-local source aliases. The selector returns exact quotes, without drafting an answer or emitting a redundant support boolean. The application maps the result to its fixed outer ID and verifies every quote occurs verbatim in its named retrieved passage before proceeding. The sampling schema contains only an evidence array; Python validates nonempty selections and treats an empty selection as insufficient evidence. Semantic support is decided by the final review. After all selections, any unsupported request makes the whole answer the standard abstention with no citations; unknown aliases, malformed decisions or invented quotes produce errors.
3. Compose each request's candidate answer directly from its validated exact quotes, removing duplicate quote strings within that request while preserving their order. There is no paraphrase/drafting model call. Each assembled request answer must fit the existing 12,000-character bound; an oversized answer produces a protocol error before review. Quotes are joined by line breaks and request answers by paragraph breaks, with the public validator trimming outer whitespace.
4. Check original-question coverage separately, without source context: a model compares the original question with the planned request list and must confirm that every requested fact and qualifier is represented without new requirements. A bounded brief assessment precedes its completeness verdict. When the plan is exactly one request equal to the original question after outer whitespace trimming, exact equality proves coverage and this extra model call is skipped. Otherwise a negative verdict produces the standard abstention; malformed verdicts produce a protocol error.
5. Review each request separately. Each review receives that request's composed quoted answer, its full cited passages (not other requests' sources), and the single planned question in labeled sections with the question last. The review distinguishes assistant-directed source commands from facts, preserves qualifiers, and checks contextual negation and exceptions. Every strict assessment/completeness verdict must pass. This review structure prevents cross-request identifier confusion but remains a fallible model judgment.

For a plan with `N` requests, a supported answer uses `2N + 2` generation calls (or three calls for a single request that exactly preserves the original question): one plan, `N` isolated selectors, one source-free coverage check and `N` isolated reviews. Empty evidence uses `N + 1` calls and skips review after all selections; rejected coverage uses `N + 2`. A negative isolated review stops early. The 16-request bound caps supported paths at 34 calls; protocol or availability failures can stop earlier. Retrieval embeddings are additional calls. The CLI `--timeout` applies to each model HTTP request, rather than the entire operation, so total elapsed time can exceed that value. The local HTTP API processes requests serially, and long inference can delay other operations.

Only a fully accepted answer is returned in request order, with source aliases mapped back to persistent citation IDs. The service independently validates the public answer contract and re-resolves retrieved passages before returning citations. Unavailable inference, invalid evidence, incomplete structured output or protocol failures return errors rather than substituted answers.

These checks distinguish mechanically verified quote provenance and source identity from model judgments about support and completeness. Isolating evidence selection prevents decisions for different requests from sharing a model response, and extractive composition cannot introduce a new paraphrased claim. A selector can still choose irrelevant, misleading or malicious instruction text, and a matching quote can omit important context, negation or qualifiers outside the selected span. The reviewer sees those full cited passages but may still miss the discrepancy. The planner, selectors and reviewer can all make mistakes. Using the same model throughout does not provide an independent factual guarantee or guarantee resistance to prompt injection. Accepted citations let a reader inspect the retrieved passages; they do not prove entailment or general hallucination resistance.

Import embeds in batches of at most 32 chunks, validates vector counts and dimensions across batches, and gathers the complete replacement before a database transaction, preserving an existing document when the model fails. Collection model checks prevent mixing vector spaces; deleting the final document permits selecting a new model. All source and document lookups include collection scope.

The local HTTP interface binds loopback only, validates Host and Origin, uses JSON requests and resolves source links through database IDs rather than filesystem paths. It has no user authentication and is a single-user local tool. Collection separation is an application boundary, not an access-control system for mutually untrusted users.

## Completion evidence

Automated regression tests exercise persistent retrieval, atomic lifecycle changes, scoped citation resolution, CLI and HTTP error paths, isolated request mapping, quote validation before composition, exact wording with deduplication and size limits, bounded call counts, and conservative handling of malformed output or negative review verdicts. Fixture verdicts test contracts and data flow; they do not establish that a real model detects semantic omissions or contradictions.

The separate live evaluations call installed embedding and generation models on synthetic FAQ documents, reopen the database, verify selective top-k retrieval against distractors, and check answerable/unsupported questions and corpus changes. The November 4 production flow described here passed 107/107 main checks (11 question cases, three selective retrieval probes, seven lifecycle checks) and 114/114 additional checks (12 question cases), using `nomic-embed-text` and `qwen2.5:3b`. All 23 question cases and their supporting passages were manually reviewed. The additional set informed development and is a regression set, not an untouched holdout. These lexical and structural checks on small synthetic corpora are not an accuracy estimate or a guarantee of grounding. Raw [main](docs/live-evaluation-2026-11-04.json) and [additional](docs/additional-evaluation-2026-11-04.json) results retain the exact source text, answers, citations, checks and timings. Earlier failed results remain available in the [validation history](VALIDATION.md).

## Modules and failure boundaries

- `store.py`: schema, chunk provenance, atomic writes and single-snapshot exact cosine reads.
- `models.py`: loopback Ollama HTTP protocol, embedding/output validation, request planning, isolated exact-quote selection, bounded extractive composition, source-free coverage checking and isolated model review.
- `service.py`: input limits, model consistency, import orchestration, retrieval, abstention and citation re-resolution.
- `cli.py` / `server.py` / `web/`: JSON CLI, single-threaded local API and browser client. Document content is rendered as text.
- `tools/evaluate_live.py`: disposable persistent corpus and actual-model evaluation; missing runtime reports blocked, never fixture success.

Vectors are normalized before storage. Signature and chunk reads use a single SQLite statement so another process cannot swap vector spaces between metadata checks and scoring. Every retrieved chunk is re-resolved after generation, including uncited passages and context used for abstention; an observed concurrent update/delete returns a retry error. Added documents and changes to unretrieved chunks are not detected by this check. This cannot guarantee a source will remain unchanged after the response reaches a reader. Original text and vectors share the same database transaction during replacement.

Stored model signatures include the configured name and vector dimension. Weight digests and task-prefix configuration are not pinned. Replacing a model tag or changing its embedding behavior requires rebuilding the affected collection. Exact retrieval and character chunking support modest local corpora; this project does not claim scalable approximate indexing or tokenizer-aware context guarantees.

The loopback HTTP boundary does not prove local inference: Ollama can support cloud models or a server can proxy requests. Obvious `:cloud`/`-cloud` names are rejected, but aliases cannot be verified. Operators must disable server cloud features (for example `OLLAMA_NO_CLOUD=1` when starting Ollama) and use installed local models. The app does not change global settings or provision model access.
